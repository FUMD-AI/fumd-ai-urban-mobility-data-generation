# Alicante City Centre SUMO Traffic Scenario Generation and FCD Extraction Workflow

## 1. Overview

This document describes a reproducible workflow for generating synthetic urban
traffic demand scenarios on an OpenStreetMap-derived SUMO network of central
Alicante, Spain, and for extracting Floating Car Data (FCD) — including
geographic coordinates and traffic-signal state — from each simulated
scenario. The workflow is documented following FAIR principles
(Findable, Accessible, Interoperable, Reusable) to support reuse, replication,
and integration into downstream traffic-analysis pipelines.

| | |
|---|---|
| **Domain** | Urban traffic microsimulation |
| **Simulator** | Eclipse SUMO 1.27.1 |
| **Network source** | OpenStreetMap (Alicante city centre) |
| **Simulation horizon** | 1800 s (30 min) |
| **Scenario matrix** | 4 traffic densities × 3 stochastic replicates = 12 scenarios |
| **Output** | Per-scenario FCD trajectory files (geo + signal state) |

## 3. Upstream Data Acquisition: OpenStreetMap Extraction and SUMO Network Conversion

This section documents the steps required to obtain the OpenStreetMap (OSM)
source data and convert it into the SUMO network file
(`Alicante_centro_ciudad.net.xml`) used as the fixed input to every scenario
in Section 6. These steps are the true starting point of the workflow and
must be reproducible independently of any SUMO scenario-generation step.

> **Provenance note.** The specific `Alicante_centro_ciudad.net.xml` used
> throughout this document was originally generated on 2018-05-07 with
> **SUMO netconvert 0.32.0**, from a source file
> `ALICANTE_centro_ciudad.osm` that is no longer available to this
> workflow, using **only** `--proj.utm true` (no other netconvert flags
> were recorded). Its embedded `<location>` element reports
> `origBoundary="-0.495075,38.336600,-0.470936,38.353021"` — this is the
> **authoritative, exact** bounding box of that file, used throughout this
> section in place of an approximated one. Re-running the steps below with
> a current OSM snapshot and the current SUMO version (1.27.1) will produce
> a network covering the *same geographic area*, but not necessarily an
> *identical* network graph — see the limitations note at the end of
> Section 3.4.

*The recommended path (Option B, below) in one picture: map → `.pbf` → `.osm` → `.net.xml`, with a validation checkpoint after each conversion.*

### 3.1 Area of interest (AOI)

The network's exact bounding box, as recorded in the file itself, is:

| | Value |
|---|---|
| West (min lon) | −0.495075 |
| South (min lat) | 38.336600 |
| East (max lon) | −0.470936 |
| North (max lat) | 38.353021 |

This spans approximately 2.11 km (E–W) × 1.83 km (N–S), consistent with the
"~2 km × 2 km" description of the AOI. If deriving a bounding box from
scratch for a *new* AOI (e.g. a different city), the same centroid-based
method still applies:

```
Δlat = 1.0 / 111.32                      # km → degrees latitude
Δlon = 1.0 / (111.32 * cos(lat₀ in rad))  # km → degrees longitude

south = lat₀ − Δlat   north = lat₀ + Δlat
west  = lon₀ − Δlon   east  = lon₀ + Δlon
```

**Coordinate order varies by tool — check this before running anything
below.** The same four numbers get passed to three different tools in
three different orders in this section. Getting it wrong doesn't always
error cleanly: `osmium extract -b` and Overpass QL both fail quietly by
clipping the wrong area rather than raising an error, so it's worth
double-checking against this table before a retrieval run rather than
after:

| Tool | Expected order | This AOI |
|---|---|---|
| `osmium extract -b` | `west,south,east,north` | `-0.495075,38.336600,-0.470936,38.353021` |
| Overpass QL `(...)` bbox filter | `south,west,north,east` | `38.336600,-0.495075,38.353021,-0.470936` |
| `pyrosm` `bounding_box=[...]` | `[minx,miny,maxx,maxy]` = `[west,south,east,north]` | `[-0.495075, 38.336600, -0.470936, 38.353021]` |

(`pyrosm` raises a clear `minx >= maxx or miny >= maxy` `ValueError` if the
pair gets swapped — the one tool of the three that fails loudly.)

### 3.2 Retrieve the OSM extract

Three reproducible retrieval methods are documented below, all using the
exact bounding box from Section 3.1. **Option B is the recommended default**
— it is the only one of the three that actually produces both artefacts
this workflow is named for, in order: a pinned, re-fetchable `.osm.pbf`
first, then the `.osm` XML netconvert consumes, derived from it rather than
queried separately. Options A and C are documented as alternatives with
their own tradeoffs, not as equally-weighted choices.

**Option B (recommended) — Regional extract + local clip with `osmium`: pbf, then osm**

```bash
# 1. Download a regional extract (Comunidad Valenciana) from Geofabrik.
#    Record the download date — Geofabrik overwrites "-latest" daily, so
#    the filename alone doesn't pin a snapshot; the date does (Section 3.4).
wget https://download.geofabrik.de/europe/spain/comunidad-valenciana-latest.osm.pbf

# 2. Clip to the exact bounding box with osmium-tool — this is the pbf-map
#    deliverable: a small, self-contained, exactly-bounded .osm.pbf.
osmium extract \
    -b -0.495075,38.336600,-0.470936,38.353021 \
    comunidad-valenciana-latest.osm.pbf \
    -o alicante.osm.pbf

# 2b. Validate before moving on — catches a swapped bbox order or an
#     accidentally-empty clip immediately, rather than after netconvert
#     fails downstream.
osmium fileinfo -e alicante.osm.pbf
# check: reported bounding box matches Section 3.1, node/way counts are non-zero

# 3. Convert to plain OSM XML — this is the osm-map deliverable that
#    Section 3.3's netconvert step consumes. Pure format conversion: no
#    re-clipping happens here, since step 2 already bounded the data.
osmium cat alicante.osm.pbf -o alicante_centro_2km.osm
```

**Option A — Overpass API (direct bbox query, no full-planet download):**

Faster for a one-off query, but it queries `.osm` XML directly and never
produces a `.pbf` at all — skip this option if a pinned, re-fetchable pbf
artefact matters for your reproducibility record. It's also more prone to
timing out or being rate-limited than Option B on a dense downtown AOI.

```bash
cat > alicante_bbox_query.overpassql <<'EOF'
[out:xml][timeout:180];
(
  way["highway"](38.336600,-0.495075,38.353021,-0.470936);
  >;
);
out body;
EOF

curl -X POST -d @alicante_bbox_query.overpassql \
    "https://overpass-api.de/api/interpreter" \
    -o alicante_centro_2km.osm
```

**Option C — `pyrosm` (Python-based extraction, validation, and network preview):**

`pyrosm` is a Python library for fast parsing of `.osm.pbf` files into
`pandas`/`geopandas` structures. It is not a replacement for `netconvert`
(SUMO still requires the `.net.xml` conversion in Section 3.3), but it is
useful for quickly validating that a downloaded `.pbf` covers the intended
AOI, and for inspecting/visualising the driving network in Python before
committing to a full SUMO conversion.

```bash
pip install pyrosm --break-system-packages
```

```python
from pyrosm import OSM

# Initialize the OSM parser object.
# bounding_box = [minx, miny, maxx, maxy] = [west, south, east, north]
# — the exact AOI recorded in Alicante_centro_ciudad.net.xml (Section 3.1).
osm = OSM(
    "alicante.osm.pbf",
    bounding_box=[-0.495075, 38.336600, -0.470936, 38.353021],
)

# Get the driving network (streets) as GeoDataFrames.
nodes, edges = osm.get_network(network_type="driving", nodes=True)

# Quick validation / QA before handing off to netconvert:
print(f"nodes: {len(nodes)}, edges: {len(edges)}")
edges.plot()  # visual sanity check of network coverage/shape
```

`alicante.osm.pbf` here is the same clipped file produced by Option B
step 2 (or any `.osm.pbf` covering the AOI — `pyrosm` applies the
`bounding_box` filter internally during parsing, so a full regional
extract can also be passed directly without pre-clipping).

All three options are valid entry points into Section 3.3, but they are not
equally weighted: Option B is the default recommendation, since it is the
only one that leaves a pinned `.osm.pbf` on disk as a reproducibility
artefact and follows the pbf-then-osm order this section is structured
around. Reach for Option A only for a disposable, lightweight one-off query
where retaining a `.pbf` doesn't matter, or Option C when a Python-side
network preview or GIS export (e.g. to GeoPackage/Shapefile via
`edges.to_file(...)`) is wanted *alongside* the SUMO conversion — note that
Option C's `bounding_box` filter works directly against the unclipped
regional `.pbf` from Option B step 1, so it doesn't require step 2's
`osmium extract` clip to already exist.

### 3.3 Convert the OSM extract to a SUMO network with `netconvert`

```bash
netconvert \
    --osm-files alicante_centro_2km.osm \
    --output-file Alicante_centro_ciudad.net.xml \
    --proj.utm
```

This minimal invocation mirrors what is actually embedded in the original
file's header (Section 3, provenance note above) — only the input file,
output file, and UTM auto-projection were specified; all other behaviour
(junction handling, traffic-light inference, geometry simplification) came
from netconvert 0.32.0's own defaults.

For a **new** network built with the current toolchain (SUMO 1.27.1), the
following extended flag set is recommended good practice. The
`--geometry.remove` through `--proj.utm` flags were used when this
document's example scenarios (Section 6 onward) were generated against a
network conceptually equivalent to the original; `--type-files` is a v1.3.0
addition not present in the bundled `Alicante_centro_ciudad.net.xml` and is
recommended for any future rebuild rather than reported as already applied
to it:

```bash
netconvert \
    --osm-files alicante_centro_2km.osm \
    --type-files "$SUMO_HOME/data/typemap/osmNetconvert.typ.xml" \
    --output-file Alicante_centro_ciudad.net.xml \
    --geometry.remove \
    --roundabouts.guess \
    --ramps.guess \
    --junctions.join \
    --tls.guess-signals \
    --tls.discard-simple \
    --tls.join \
    --output.street-names \
    --proj.utm
```

| Flag | Purpose |
|---|---|
| `--type-files osmNetconvert.typ.xml` | Uses SUMO's own maintained OSM-tag → edge-type mapping (bundled with every SUMO install) instead of netconvert's generic built-in defaults — improves classification of lane counts, speed limits, and road-type-specific rules straight out of OSM tags. Not present in the original 2018 invocation (provenance note above) or in v1.2.0 of this document; recommended for any *new* network build. |
| `--geometry.remove` | Removes redundant shape-only nodes, simplifying the network graph without changing road geometry. |
| `--roundabouts.guess` | Infers roundabout structures from OSM way topology. |
| `--ramps.guess` | Infers highway on-/off-ramps. |
| `--junctions.join` | Merges clusters of nearby nodes (common at complex OSM-mapped intersections) into single logical junctions. |
| `--tls.guess-signals` | Infers signalised (traffic-light-controlled) junctions from OSM tags and geometry. |
| `--tls.discard-simple` | Removes trivial/unnecessary traffic-light logic at junctions that don't need it. |
| `--tls.join` | Consolidates multiple close-together signal-controlled nodes into one coordinated traffic light program — required for the `--fcd-output.signals` field (Section 7) to report meaningful signal states. |
| `--output.street-names` | Preserves OSM street names in the network for traceability back to the source data. |
| `--proj.utm` | Automatically selects the correct UTM zone for the AOI, ensuring accurate metre-based internal coordinates and correct back-projection to WGS84 for `--fcd-output.geo` (Section 7). |

### 3.4 Record data provenance and reproducibility limitations

To keep this stage reproducible, log alongside `Alicante_centro_ciudad.net.xml`:

- The exact bounding box used (Section 3.1) — for this network,
  `-0.495075,38.336600,-0.470936,38.353021`.
- The retrieval method (Option A, B, or C), source URL, and **retrieval
  timestamp** — OSM is a live-edited dataset, so the same bbox query run
  on a different date may return a different network.
- The `netconvert` version and exact flag set used
  (`netconvert --version`).
- The `osmium-tool` (or `osmconvert`) version used for extraction/clipping
  (`osmium --version`), if Option B was used.
- Optionally, the Overpass API changeset ID or the Geofabrik extract's
  publication date, for exact dataset pinning.

**Known limitation for this specific network.** Byte-for-byte or even
topologically identical reproduction of the original
`Alicante_centro_ciudad.net.xml` is **not achievable** with the steps
above, because: (a) the original source file `ALICANTE_centro_ciudad.osm`
is not retained/available — only a re-query of current OSM data for the
same bbox is possible, and OSM has been edited continuously since 2018;
and (b) the original was built with netconvert 0.32.0, while this
workflow's toolchain uses netconvert 1.27.1, whose default heuristics and
OSM tag handling have changed over eight years of releases. The steps in
this section reconstruct a network covering the *same geographic extent*
using current best practice, not a verified byte-identical copy of the
uploaded file.

### 3.5 Validate the converted network

Before using the network for scenario generation, confirm it loads cleanly:

```bash
sumo -n Alicante_centro_ciudad.net.xml --no-step-log --end 1
```

A clean exit (no `Error:` lines) confirms the network is syntactically valid
and ready to be used as the fixed input `Alicante_centro_ciudad.net.xml`
referenced throughout the rest of this document (Section 6 onward).

As a quick sanity check on top of the syntactic validation above, confirm
the edge count looks reasonable for a dense ~2km × 2km city-centre AOI (not
near-zero, which usually indicates the bbox order was swapped in Section
3.2):

```bash
grep -c "<edge " Alicante_centro_ciudad.net.xml
```

## 4. Workflow Pipeline

```
                 ┌───────────────────────────┐
                 │ OSM extract (Section 3)    │
                 │ Overpass API / Geofabrik   │
                 └─────────────┬─────────────┘
                                │ netconvert
                                ▼
                 ┌───────────────────────────┐
                 │ Alicante_centro_ciudad     │
                 │ .net.xml  (SUMO network)   │
                 └─────────────┬─────────────┘
                                │
                                ▼
                 ┌───────────────────────────┐
                 │ randomTrips.py             │
                 │ (stochastic OD generation, │
                 │  min-distance filter)      │
                 └─────────────┬─────────────┘
                    .trips.xml │
                                ▼
                 ┌───────────────────────────┐
                 │ duarouter (invoked via -r) │
                 │ route validation & repair  │
                 └─────────────┬─────────────┘
                      .rou.xml │
                                ▼
                 ┌───────────────────────────┐
                 │ <prefix>.sumo.cfg          │
                 │ (net + route + time + seed)│
                 └─────────────┬─────────────┘
                                ▼
                 ┌───────────────────────────┐
                 │ sumo (microsimulation)     │
                 │ --fcd-output.geo true      │
                 │ --fcd-output.signals true  │
                 └─────────────┬─────────────┘
                                ▼
                 ┌───────────────────────────┐
                 │ fcd_signals_<density>_     │
                 │ <replicate>.xml            │
                 └───────────────────────────┘
```

**Stage 1 — Trip generation** (`randomTrips.py`): samples random
origin–destination pairs on the network edges, subject to a minimum
straight-line trip distance, and spaces departures evenly across the
simulation horizon to approximate a target vehicle count.

**Stage 2 — Routing** (`duarouter`, invoked internally by `randomTrips.py -r`):
computes a shortest/fastest path for each trip and validates connectivity,
discarding or retrying trips whose origin and destination are not mutually
reachable.

**Stage 3 — Configuration assembly**: a `.sumo.cfg` is written binding the
network, the generated route file, the simulation time window, and the
random seed used for trip generation (for full reproducibility of the
microsimulation's own stochastic sub-processes, e.g. car-following noise).

**Stage 4 — Simulation & FCD extraction** (`sumo`): runs the microsimulation
to completion and streams per-vehicle, per-timestep floating car data
(position in geographic coordinates, plus traffic-signal state) to an
output XML file.

## 6. Data and File Naming Convention

| File | Pattern | Description |
|---|---|---|
| Network | `Alicante_centro_ciudad.net.xml` | Static OSM-derived road network (shared across all scenarios) |
| Trips | `Alicante_<density>_<rep>.trips.xml` | Raw stochastic origin–destination trip definitions |
| Routes | `Alicante_<density>_<rep>.rou.xml` | Validated, routed vehicles ready for simulation |
| Configuration | `Alicante_<density>_<rep>.sumo.cfg` | SUMO run configuration (inputs, time window, seed) |
| FCD output | `fcd_signals_<density>_<rep>.xml` | Per-timestep trajectories with geo-coordinates and signal state |

`<density>` ∈ {900, 1000, 1200, 1400} (target vehicle count over the 1800 s
window). `<rep>` ∈ {1, 2, 3} (independent stochastic replicate, distinguished
solely by random seed).

| Scenario ID | Target vehicles | Insertion period (s/veh) | Random seed |
|---|---|---|---|
| Alicante_900_1 | 900 | 2.0000 | 3001 |
| Alicante_900_2 | 900 | 2.0000 | 3002 |

### 7.3 Worked example — `Alicante_900_1`

**Trip and route generation:**
```bash
python3 "$SUMO_HOME/tools/randomTrips.py" \
    -n Alicante_centro_ciudad.net.xml \
    -o Alicante_900_1.trips.xml \
    -r Alicante_900_1.rou.xml \
    -b 0 -e 1800 \
    -p 2.0 \
    --seed 3001 \
    --fringe-factor 5 \
    --min-distance 500 \
    --validate \
    --vehicle-class passenger \
    --trip-attributes "departLane=\"best\" departSpeed=\"max\""
```

**Resulting configuration file (`Alicante_900_1.sumo.cfg`):**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xsi:noNamespaceSchemaLocation="http://sumo.dlr.de/xsd/sumoConfiguration.xsd">

    <input>
        <net-file value="Alicante_centro_ciudad.net.xml"/>
        <route-files value="Alicante_900_1.rou.xml"/>
    </input>

    <time>
        <begin value="0"/>
        <end value="1800"/>
    </time>

    <processing>
        <ignore-route-errors value="true"/>
    </processing>

    <random_number>
        <seed value="3001"/>
    </random_number>

</configuration>
```

**FCD extraction:**
```bash
sumo -c Alicante_900_1.sumo.cfg \
    --fcd-output.geo true \
    --fcd-output.signals true \
    --fcd-output ../fcd_signals_900_1.xml \
    --end 1800
```

**Observed result** (this run): 900/900 target vehicles inserted; mean
route length ≈ 1411 m; simulation completed at t = 1800 s with no fatal
errors. This is one data point of provenance — see Section 8.

## 8. Provenance and Validation

For full reproducibility and auditability, each scenario generation run
should log (and, where retained, this workflow did log):

1. The exact `randomTrips.py` invocation and seed (Section 7.3).
2. The **actual** number of vehicles inserted, compared against the
   target (`grep -c "<vehicle " <file>.rou.xml`, or the `Inserted:` line
   from `sumo --duration-log.statistics`).
3. Any SUMO runtime warnings (teleports, emergency braking), which are
   expected, physically meaningful congestion artefacts at higher
   densities rather than configuration errors — e.g. in this dataset,
   `Alicante_1400_1` and `Alicante_1400_2` each inserted 1399/1400
   vehicles because a small number of departures could not merge into
   gridlocked lanes before the simulation horizon ended.

This provenance information should be versioned alongside the data
(e.g. as a `provenance.log` or embedded in a data-package `README`) so
that any consumer of the FCD outputs can assess fitness for use without
re-running the simulation.

## 9. Automation Scripts (Reusability Interface)

| Script | Purpose | Signature |
|---|---|---|
| `generate_scenario.sh` | Generates one scenario's trips, routes, and config | `./generate_scenario.sh <net_file> <num_cars> <sim_end_seconds> <seed> <out_prefix> [min_distance]` |
| `generate_fcd_outputs.sh` | Batch-runs SUMO on all `Alicante_*_*.sumo.cfg` files, producing FCD outputs | `./generate_fcd_outputs.sh [end_time]` |

Example — regenerating the full 4×3 matrix from scratch:
```bash
SEED=3001
for density in 900 1000 1200 1400; do
  for rep in 1 2 3; do
    ./generate_scenario.sh Alicante_centro_ciudad.net.xml \
        "$density" 1800 "$SEED" "Alicante_${density}_${rep}" 500
    SEED=$((SEED + 1))
  done
done
./generate_fcd_outputs.sh 1800
```
